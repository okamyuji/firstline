# ADR-0001 単一ノードのGoとSQLiteで始める

状態は採用です。

## 状況

firstlineは先着チケットと整理券の販売サービスで、販売開始の直後に同時接続が集中します。RailsとMySQLをクラウドで動かす構成では、利用者が少ない時期にも運用費がかかります。求められているのは小さく始めて規模が要るようになった時点でPostgreSQLかMySQLへ移れる構成です。

## 決定

AWSのEC2の1台（Linux）で、SQLiteを組み込んだ単一のGoバイナリを動かします。SQLiteドライバはcgoの要らない`modernc.org/sqlite`です。

| 項目 | 決定 |
|---|---|
| 接続 | 同じファイルをWriteDBとReadDBの2つで開く。WriteDBは接続1本、ReadDBは`file:`で始まる接続文字列に`mode=ro`を付ける |
| PRAGMA | 接続文字列の`_pragma`と短縮キーで渡し、プールが開くどの接続にも同じ設定を入れる |
| 書き込み | 書き込みゴルーチン1つが、容量8192のチャネルから項目を受けてグループコミットする |
| 在庫 | 正本は`event_sales.remaining`の条件付きの更新にする。`Inventory`のメモリ実装を事前判定に置き、起動時にWriteDBから作り直す |
| チェックポイント | アプリは`wal_autocheckpoint=0`にし、Litestreamに任せる |
| 複製 | LitestreamでCloudflare R2へ1秒ごとに送る |

設定値の詳細は基本設計書の「接続設定」と「配備」の節にあります。

## 理由

SQLiteの書き込みは同時に1つしか進みません。書き込みを1つのゴルーチンに集めれば、待ちはSQLiteのロックの奪い合いでなくGoのチャネルの順番になります。グループコミットで1回のfsyncに多くの項目をまとめられるのも、この形の利点です。

ReadDBを`mode=ro`で開くのは、読み取りの経路から誤って書き込むことをなくすためです。ドライバの文書によれば、`mode=ro`の接続ではすべての書き込みが`SQLITE_READONLY`で失敗します。`_query_only=1`は後のPRAGMAで解除できるので採りません。

チェックポイントをLitestreamに任せる理由は[Litestreamの文書](https://litestream.io/tips/)の推奨にあります。アプリが自動でチェックポイントすると、LitestreamがWALの更新を取りこぼしてスナップショットを取り直すためです。

在庫をメモリに置けば販売開始の直後の判定がDBの往復なしで済みます。保留と購入確定は応答の前に同期で書くので、WriteDBの内容から在庫を正しく作り直せます。

## 結果

受け入れる制約は次のとおりです。

1. ホスト1台の停止がそのままサービスの停止になります。復旧は別のホストへの復元で行うため、復元の時間だけ止まります。
2. 応答の前のfsyncが守るのは、ホストのディスクに残った購入までです。Litestreamの複製は非同期なので、ディスクごとホストを失うと直前の約1秒の変更を失います。決済が完了したのに購入の記録がない状態はここで起こりえます。復元の後に`firstline reconcile`で完了済みの決済を照合し、記録のない決済を払い戻して解消してください。
3. メモリ在庫は1つのプロセスの中でしか共有できません。HTTPを複数のホストに広げるときは、メモリの事前判定を外してDBの実装へ替えます（ADR-0003）。
4. Litestreamが止まるとWALが伸び続けます。`/healthz`でWALの大きさを見せ、1GiBを超えたら警告を出して気づけるようにしています。
5. ログインの失敗回数はメモリにあり、再起動でなくなります。

この制約のどれかが受け入れられなくなった時点が、ADR-0003で規模拡大を判断する時点です。
