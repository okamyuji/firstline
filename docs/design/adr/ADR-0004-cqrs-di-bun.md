# ADR-0004 CQRS、DI、Bunと方言別SQLファイルを採る

状態は採用です。

## 状況

ADR-0003はSQLiteからPostgreSQLかMySQLへ業務ロジックを変えずに移れることを前提にしています。この前提を守るために要るのは保存先と在庫の実装を差し替えられる構成と、方言の違いを閉じ込める場所です。

## 決定

| 項目 | 決定 |
|---|---|
| CQRS | 書き込み側はWriteDB、メモリ在庫、グループコミットを使う。読み取り側はReadDBと読み取り用の表`event_sales`を使う |
| DI | 各層はinterfaceで受け取る。`cmd/firstline`の組み立て関数1か所で手動で注入する。DIコンテナは使わない |
| SQLの実行 | Bun（`github.com/uptrace/bun`）の`db.NewRaw`で実行する |
| SQLの置き場 | 方言ごとの`.sql`ファイルを`internal/store/<方言>/sql/`に置き、`embed.FS`で読む。Goの文字列にSQLを書かない |
| 時刻の列 | UTCのUnixミリ秒を`BIGINT`の列に置き、Goで`time.Time`へ変換する |
| 使わないもの | sqlc、GORM、DIコンテナ |

## 理由

ReadDBとWriteDBの分離は、そのまま書き込みと読み取りの境界になります。書き込みはWriteDBとグループコミットの規則に、読み取りはReadDBの設定にそれぞれ従うので、2つを別の経路にしたほうが設定と責任が混ざりません。

DIを組み立て関数1か所で行えば、どの実装が使われているかをその関数を読むだけで確かめられます。差し替え口は基本設計書の構成の節に並べたとおりで、手動の注入で十分に扱える数です。

[Bunの文書](https://bun.uptrace.dev/guide/query-select.html)によれば、`db.NewRaw`は任意のSQLを実行し、結果を構造体へ読み込めます。BunはSQLite、PostgreSQL、MySQLの方言を持つので、接続と結果の読み込みは3つのDBで共通です。SQLそのものは方言ごとのファイルに分けるため、方言の違いはファイルの中だけに収まります。時刻を整数の列に置くのも同じ理由です。`modernc.org/sqlite`は既定で時刻を文字列として保存するので、DBの時刻型に任せると3つのDBで比較のSQLが変わります。

sqlcはSQLからGoのコードを生成するツールです。生成したコードは方言ごとに別の型になり、生成の手順も保守の対象に加わります。GORMはSQLを組み立てる処理を隠すため、方言ごとに実際のSQLを確かめる手間が増えます。この理由からどちらも採りません。

## 結果

SQLを足すときは、3つの方言のファイルを同じ変更で足します。足し忘れを見つけるのはtestcontainersで3つのDBに同じテストを通すCIです。

Bunは`?`に渡した値をエスケープしてからSQLへ埋め込みます。SQLの値は必ず`?`で渡し、文字列の連結でSQLを組み立てないでください。
