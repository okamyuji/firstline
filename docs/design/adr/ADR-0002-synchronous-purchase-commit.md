# ADR-0002 購入確定を同期書き込みにする

状態は採用です。

## 状況

firstlineはWALモードのSQLiteへ、グループコミットでまとめて書きます。WALモードで`synchronous=NORMAL`にすればコミットのたびのfsyncが省かれ、書き込みは速くなります。[Litestreamの文書](https://litestream.io/tips/)が勧めているのもこの設定です。

一方で[SQLiteの文書](https://www.sqlite.org/pragma.html#pragma_synchronous)は、WALモードで`synchronous=NORMAL`のときにコミットした取引が、電源断やOSの停止の後に巻き戻ることがあると述べています。購入確定の応答を返した後でその購入が巻き戻ると、購入者は払ったのに席がなく、その席は別の人に売られます。

## 決定

WriteDBを`synchronous=FULL`で開きます。購入の状態を変える書き込みは同期項目とし、コミットが戻るまで応答を返しません。対象は保留の作成、`payment_id`の記録、購入確定、決済の失敗、期限切れ、払い戻しの開始と完了です。イベント作成、主催者の作成、ログイン、ログアウト、メールの送信済みの記録も同期項目に含めます。

課金ログは購入確定と払い戻しの状態遷移と同じトランザクションで書きます。独立した書き込みにはしません。

アクセスログ、セッションの最終操作時刻、失効したセッションの削除は非同期項目です。呼び出し側はチャネルへ送るだけで待たず、書き込みゴルーチンが64件たまるか15msが過ぎた時点でまとめてコミットします。

同期項目が届いたら、書き込みゴルーチンはチャネルにすでにある項目を待たずに取り出し、64件に達するかチャネルが空になった時点でコミットします。同期項目が15msを待つことはありません。

## 理由

SQLiteの文書によれば、WALモードで`synchronous=FULL`にするとコミットのたびにWALファイルのfsyncが1回増えます。取引が電源断をまたいでも失われないのは、このfsyncがあるためです。

fsyncの回数はグループコミットで抑えます。販売開始の直後のように同期項目が続けて来るときは、チャネルにたまった最大64件が1回のコミットにまとまり、fsyncも1回で済みます。

課金ログを状態遷移と同じトランザクションに入れるのは、状態が変わったのに課金の記録がない状態をなくすためです。アクセスログとセッションの時刻は電源断で数件なくなっても購入の正しさに影響しないので、非同期に残します。

## 結果

購入確定の応答時間にはfsync1回分の時間が加わります。この時間はディスクの性能で決まるので、配備先のディスクで負荷試験を行って測ってください。測った値はADR-0003の書き込み量の判断の材料です。

この決定が保証するのはローカルのディスクに残るところまでです。ホストごと失う場合の損失はADR-0001の制約に従います。
