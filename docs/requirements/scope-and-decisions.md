# firstlineの範囲と決定事項

## 目的

スタートアップはRailsとMySQLをクラウドで動かすと運用費が重くなります。firstlineはGoとSQLiteの単一バイナリで小さく始め、成長したらMySQLかPostgreSQLへ移せる構成にするので、初期の運用費と規模を広げた後の運用費がどちらも下がります。

構成は単一のGoバイナリにSQLiteを組み込み、ReadDBとWriteDBを分ける形です。頻繁に変わる状態はメモリに置き、ログは15msのグループコミットで書くので、ディスクへの書き込み回数が減ります。複製先はLitestreamで送るCloudflare R2です。

## 題材

firstlineは先着チケットと整理券の販売サービスです。小規模なイベントやライブの先着販売を扱います。販売開始の直後に同時接続が集中します。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 移行の範囲 | 業務ロジックと保存先を差し替え口で分け、SQLite、PostgreSQL、MySQLの3実装を作る。testcontainersで同じテストを3つのDBに通す。SQLiteからPostgreSQLとMySQLへデータを移すコマンドを作る | 移行できる構成かどうかは、実際に移して動かすまで確かめられないため |
| 在庫の判定 | 席の数の正本はDBの条件付きUPDATEにする。単一マシンでは`Inventory`のメモリ実装を事前判定に置き、複数マシンでは事前判定を外す | 単一マシンのメモリ在庫は複数マシンで共有できないため |
| 決済 | 決済の差し替え口と、非同期の完了通知を出す模擬実装を作る。Stripe実装は作らない | 鍵がなくてもCIですべての経路を動かせるため |
| 期限切れ後の決済完了 | 保留の期限切れ後に完了通知が届いたら、自動で払い戻す。TLA+の主な検証対象にする | 二重販売と「払ったのに席がない」状態を防ぐため |
| 購入確定の永続性 | 購入の確定は同期書き込みにする。WriteDBは`synchronous=FULL`にし、fsyncの完了を待ってから応答する。課金ログは購入確定と払い戻しの状態変更と同じトランザクションで書き、アクセスログは15msのグループコミットに残す | WALと`synchronous=NORMAL`の組み合わせでは、電源断で直前のコミットが消えうるため |
| CQRS | 書き込み側はWriteDB、メモリ在庫、グループコミットを使う。読み取り側はReadDBと読み取り用の表を使う | ReadDBとWriteDBの分離がそのまま書き込みと読み取りの境界になるため |
| DI | 各層はinterfaceで受け取る。`cmd/`の組み立て関数1か所で手動で注入する。DIコンテナは使わない | 層どうしを疎結合にし、保存先と在庫の実装を差し替えられるようにするため |
| SQL | Bun（uptrace/bun）を使う。SQLはGoの文字列に書かず、方言ごとの`.sql`ファイルに置き、`db.NewRaw`で実行する。sqlcとGORMは使わない | BunはSQLite、PostgreSQL、MySQLの方言を持ち、生のSQLも書けるため。コード生成は保守の負担になるため使わない |
| Goの書き方 | modern-go-guidelinesの最新版に従う。Goファイルを編集する前に`list --file-path`で指針を確かめる | 対象のGoの版に合った書き方へそろえるため |
| 状態遷移 | 暗黙の状態遷移をすべて明示的なモデルに書き直す。そのモデルのTLA+仕様を作り、TLCですべてのケースを検証する | 保留、購入、期限切れ、払い戻しの競合を網羅して確かめるため |
| SQLiteドライバ | `modernc.org/sqlite`を使う | cgoなしで静的な単一バイナリにできるため |
| 認証 | 主催者はArgon2idで保存したパスワードとセッションCookieで認証する。購入者はアカウントを作らず、メールアドレスと購入ごとの署名付きトークンで購入を照会する | 販売開始の直後の集中時に、購入者の登録処理を挟まないため |
| 画面の範囲 | embed.FSで同梱する画面は、購入者の一覧、詳細、購入、照会と、主催者のログイン、イベント作成、販売状況にする | 購入の経路と、販売を始めて状況を見る主催者の最小の操作を画面で確かめられるようにするため |
| メール | 保留の作成、購入確定、払い戻しを購入者へメールで知らせ、照会トークンもメールで渡す。保留の通知には決済の期限を書き、期限までに決済を終えないと席は確保されないことを伝える。送る時点で保留が続いていなければ、保留の通知は送らない。メール送信の差し替え口と模擬実装を作り、実際の送信サービスの実装は作らない。メールの言語は購入時の言語を購入に保存して決める | 鍵がなくてもCIですべての経路を動かせるため。決済の完了通知と払い戻しはリクエストの外で起こり、`Accept-Language`がないため |
| 画面の技術 | サーバーがGoの`html/template`で描画し、部分の更新はhtmxで行う。ReactやVueは使わない | 画面の数が少なく、ビルドの工程とJavaScriptの依存を増やさずに単一バイナリへ同梱できるため |
| 観測 | ホストはAWSのEC2にする。ログはsystemdがファイルへ追記したものをCloudWatch Agentで、指標はEmbedded Metric FormatでCloudWatchへ送る。エラーの通知は差し替え口にし、初期の実装はログとCloudWatchのアラームにする。Sentryなどの実装は作らず、移る条件をADR-0005で決める | 初期の運用費を抑えつつ、エラーの調べやすさが足りなくなった時点で移れるようにするため |
| 文字列の言語 | 画面、メール、クライアントへ返すエラー文のように利用者が読む文字列は日本語と英語で持ち、ブラウザの`Accept-Language`で自動で切り替える。どちらにも合わないときは日本語を出す。ログ、サーバー内部のエラー文、CLIの出力は英語にそろえる | 海外からの購入者も同じ画面で購入できるようにするため。題材は国内の小規模イベントなので、既定は日本語にする。運用者が読む文字列は翻訳しない |
| 品質ゲート | go fmt、go vet、golangci-lint、staticcheck、`go test --count=1`、go buildに加え、カバレッジ80%以上、変更行の変異テストで全変異を殺す、CRAP 15以下、gitleaks、E2Eを課す | 変更のたびに同じ基準で品質を確かめるため |

## ADR

`docs/design/adr/`に次のADRを置きます。中心はADR-0003で、SQLiteから規模を広げるときの判断はこのADRで行います。

| ID | 題 | 決めること |
|---|---|---|
| ADR-0001 | 単一ノードのGoとSQLiteで始める | 単一バイナリ、ReadDBとWriteDBの分離、メモリ在庫、Litestreamによる複製を採る理由と、受け入れる制約 |
| ADR-0002 | 購入確定を同期書き込みにする | 購入確定は`synchronous=FULL`で応答前にfsyncし、アクセスログは15msのグループコミットに残す理由 |
| ADR-0003 | SQLiteからの規模拡大の判断基準と移行先 | PostgreSQLかMySQLへ移る条件（複数ノードの要否、書き込み量、DBの大きさ、復旧時点の要件、全文検索の要否）を測れる値で決める。移行先の選び方、在庫実装をメモリからDBへ替える手順、データ移行コマンドの使い方を決める |
| ADR-0004 | CQRS、DI、Bunと方言別SQLファイルを採る | 保存先を差し替えられる構成にする理由と、コード生成を使わない理由 |
| ADR-0005 | 観測をCloudWatchで始め、移る基準を決める | 初期の観測の構成と、Sentryなどへ移る条件を測れる値で決める。移る手順を決める |

## 設計書で決めること

- SQLiteとLitestreamの公式文書を根拠に決める、上の決定と各設定値の対応表（ReadDBの`mode=ro`、WAL、mmap、`cache_size`、`wal_autocheckpoint=0`、容量8192のチャネル、64件または15ms、Drain、systemd、embed.FS、Litestreamの設定と復元スクリプト）
- `modernc.org/sqlite`でのReadDBの読み取り専用の指定方法と、各PRAGMAを接続文字列で渡す書き方
- 認証の詳細（セッションの保存先と有効期限、購入照会トークンの署名方式と有効期限、主催者ログインの試行回数の制限）
- 各画面の項目と遷移
- 利用者が読む文字列の持ち方（翻訳の置き場、`Accept-Language`の照合方法、メールの言語の決め方、内部エラーをクライアント向けの文に変える箇所）
